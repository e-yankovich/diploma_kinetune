# Documentation strategy

## Approach

- **Code-first specification.** The OpenAPI 3.1 document is generated from the FastAPI code (routers, Pydantic models, error models), so it cannot drift from the implementation. `backend/scripts/export_openapi.py` writes it to [`schemas/openapi.json`](schemas/openapi.json), which is version-controlled.
- **Linted.** The specification is checked with **Redocly CLI** (`recommended` rules, plus "every operation has a 4XX response" as an error). Accepted exceptions are listed with a reason in [`.redocly.lint-ignore.yaml`](.redocly.lint-ignore.yaml).
- **Hand-written guides** (Markdown) add what a generated reference cannot: getting started, a tutorial, the error taxonomy, architecture and the meaning of the domain fields.
- **Real examples.** Example requests and responses are taken from the running API with the imported library ([examples/requests.http](examples/requests.http)).

## Tools

| Tool | Use |
|---|---|
| FastAPI | Generates the OpenAPI document; serves Swagger UI (`/docs`) and ReDoc (`/redoc`) |
| Redocly CLI 1.25 | Lints the specification |
| Markdown + Mermaid | Guides and diagrams (rendered by GitHub) |

Commands (from the repository root):

```bash
# regenerate the specification after an API change
docker run --rm -v "$PWD:/repo" -w /repo/backend <backend image> python scripts/export_openapi.py
# lint it
docker run --rm -v "$PWD/docs/api:/spec" -w /spec node:22-alpine npx --yes @redocly/cli@1.25.11 lint
```

## Conventions

| Topic | Rule |
|---|---|
| Paths | Plural nouns, lower case, no verbs: `/exercises`, `/exercises/{exercise_id}` |
| Fields and parameters | `snake_case`, same names as the database columns where possible |
| Enumerations | Lower-case `snake_case` values, defined once in `app/schemas/` |
| Errors | One body for all errors; stable `code` values ([errors](reference/errors.md)) |
| Methods | `GET` reads, never changes data (all current endpoints are safe and idempotent) |
| Folder structure | `guides/` (tasks), `reference/` (endpoints, models, errors), `examples/` (runnable requests), `schemas/` (specification) |
| Formatting | One H1 per page; tables for parameters and codes; JSON examples formatted with 2 spaces |

## Versioning

- The major version is in the path: `/api/v1`. A breaking change (removing or renaming a field, changing a type or a status code) needs `/api/v2`; additions (new fields, endpoints, optional parameters) stay in v1.
- `info.version` in the specification follows semantic versioning; every change is recorded in the [changelog](CHANGELOG.md).

## Known gaps

- **Prototype slice only:** authentication, coach and participant endpoints are not implemented yet, so the authentication guide describes the planned design only.
- **No pagination:** the library is small (about 100 exercises), so lists return all items. Pagination will be added when a list can grow without limit (sessions, check-ins).
- **No rate limits yet:** planned per coach account, never per IP address.
- The specification is regenerated by hand; a CI check that it matches the code is planned with the CI/CD pipeline.
